## 一、总体技术架构

系统采用**五层单向依赖**结构，层与层之间只通过接口交互，替换任意一层不影响其他层。

```
┌─────────────────────────────────────────────┐
│ 表现层   Flask + SocketIO · Streamlit × 3    │  主控台、三个分析界面
├─────────────────────────────────────────────┤
│ 调度层   子进程管理 · 任务分发 · 实时推送      │  启停引擎、日志采集、异常兜底
├─────────────────────────────────────────────┤
│ 智能体层 检索 → 撰写 → 反思 → 定稿            │  三个分析引擎同构
├─────────────────────────────────────────────┤
│ 能力层   LLM 接口 · 联网检索 · 本地情感模型     │  可插拔的外部能力
├─────────────────────────────────────────────┤
│ 数据层   PostgreSQL · 文件产物                │  业务数据与报告存档
└─────────────────────────────────────────────┘
```

**设计取舍**：没有引入 LangChain、AutoGen 等 Agent 框架，全部用原生 Python 手写调度。
好处是逻辑透明、可调试、依赖少；代价是需要自己实现工具调用与容错。

## 二、技术选型与理由

| 能力域 | 技术选型 | 选型理由 |
| :--- | :--- | :--- |
| 大模型接入 | openai SDK | 统一 OpenAI 兼容协议。换厂商只改 `base_url` 与模型名，业务代码零改动 |
| Web 服务 | Flask + Flask-SocketIO | 轻量、可控。SocketIO 用于把分析过程实时推送到浏览器 |
| 分析界面 | Streamlit × 3 | 每个引擎一个独立应用，先做原型快；按需启动节省内存 |
| 数据存储 | PostgreSQL + SQLAlchemy | 结构化存储热搜、帖子、评论、报告元信息；ORM 屏蔽 SQL 差异 |
| 联网检索 | 博查 / Anspire / Tavily | 三种服务可切换，按配额与成本选择；接口均封装为同构工具类 |
| 网页采集 | Playwright | 真实浏览器驱动，可处理登录态与 JS 动态渲染 |
| 本地推理 | PyTorch + Transformers | 多语言情感分类模型，CPU 即可推理，判断正/负面倾向 |
| 报告渲染 | HTML 模板 + Chart.js | 章节级渲染，图表配置校验失败时自动降级为表格 |
| 进程调度 | Python subprocess | 用子进程隔离三个引擎，单个崩溃不影响主控台 |

## 三、核心技术机制

### 3.1 Reflection 反思循环（系统核心）

**问题**：大模型"一次搜索就写"，必然出现素材不相关、遗漏关键方、深度不够。

**做法**：让模型自己检查自己的产出，不满意就再搜一轮。

```
段落主题
   ↓
① 首轮检索 ──→ ② 生成初稿
                     ↓
              ③ 自我检查：还缺什么？
                     ↓
              ④ 生成新查询 → 补搜 → 改写
                     ↓
              （循环 N 轮，默认 2 轮）
                     ↓
                  段落定稿
```

日志实证（真实运行记录）：

```
反思 1/2 …
  反思查询: 2026 体操世锦赛 女团 美国队 失误 得分 细节
  反思推理: 当前段落已涵盖竞争格局概述，但缺乏对手具体失误细节…
找到 10 个反思搜索结果
✓ 反思 1 完成
```

**效果**：第一轮只能写出"中国队夺冠"这种泛泛结论；第二轮补搜后才拿到
"165.764 分""终结美国队七连冠""队员名单"这类可核查的具体事实。

**可调参数**（配置层修改，无需改代码）：

| 参数 | 默认 | 影响 |
| :--- | :--- | :--- |
| `MAX_REFLECTIONS` | 2 | 反思轮数。调大更深入，耗时与 token 成本线性上升 |
| `MAX_PARAGRAPHS` | 5 | 报告段落数。决定篇幅 |

### 3.2 多智能体协同：论坛式交叉印证

**问题**：三个引擎数据源不同（本地库 / 联网新闻 / 深度报道），各写各的会产生结论冲突。

**做法**：引入一个"论坛"作为共享观点池。

```
InsightAgent ─┐
MediaAgent   ─┼──→ ForumEngine（监听日志 → 生成 HOST 点评 → 写回共享日志）
QueryAgent   ─┘         ↓
                    各引擎读回点评，影响后续思考
```

**工程实现**：不用消息队列，靠**文件变化监听 + 共享文件**实现跨进程协同。
理由：三个引擎已经是独立进程，再引入 MQ 会显著增加部署复杂度，而日志文件本身
就是天然的事件流。

**价值**：结论冲突在成稿前暴露；同时保留分歧表述，避免强行统一口径。

### 3.3 报告生成流水线

报告不是"让模型写一篇 HTML"，而是六阶段流水线：

| 阶段 | 动作 | 输出 |
| :--- | :--- | :--- |
| 1 模板选择 | 大模型从模板库中选最匹配的模板 | 模板名 + 选择理由 |
| 2 模板切片 | 把模板拆成章节骨架 | 章节列表 |
| 3 布局设计 | 生成标题与行文基调 | 文档结构 |
| 4 篇幅规划 | 给每章分配字数预算 | 章节目标 |
| 5 逐章撰写 | 每章一次模型调用 | 章节内容 |
| 6 渲染输出 | 填充模板 + 图表校验 | HTML / Markdown / IR |

**容错设计**：模型生成图表配置时经常出现 JSON 语法错误或数据格式不符。
系统内置图表审查服务：先校验 → 尝试自动修复 → 修复失败则**降级为表格**展示，
保证报告不会因为一张图崩掉。

### 3.4 数据流与三条数据来源

| 来源 | 获取方式 | 依赖 |
| :--- | :--- | :--- |
| 热搜标题 | 聚合热搜 API | 无（公开接口） |
| 网页正文 | 联网检索服务 | 需要检索 API Key |
| 平台帖子与评论 | Playwright 深度采集 | 需要人工扫码登录平台 |

**工程结论（实测）**：缺少真实数据时，引擎不会报错，而是让大模型自由发挥，
产出一份"格式专业、数据虚构"的报告。因此系统设计上必须以
`select count(*) from weibo_note` 之类的库内校验作为报告可信度的前置判断。

## 五、可扩展方向

1. **检索结果缓存**：同一查询短期内重复率高，加缓存可显著降本。
2. **多级审批流**：报告发布前增加人工复核节点，适配政企场景。
3. **订阅式监控**：定时任务 + 关键词订阅，变"按需分析"为"持续监测"。
4. **模型分级**：重要章节用强模型，背景章节用轻模型，平衡质量与成本。
